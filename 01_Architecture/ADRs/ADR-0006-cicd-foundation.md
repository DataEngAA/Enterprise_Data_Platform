# ADR-0006: CI/CD Foundation — Two-Hop OIDC Trust, Bootstrap/Logging Exclusion, and Manual-Approval Apply

Status: **Proposed. Implementation slice 1 (AWS OIDC trust only) written to `infrastructure/terraform/bootstrap/` source (2026-08-07) — not yet applied to real AWS. Implementation slice 2A (PR validation workflow, `.github/workflows/terraform-ci.yml`) also written to source (2026-08-07) — `terraform fmt`/`init -backend=false`/`validate` per stack plus a pinned Checkov scan (Terraform 1.15.8, Checkov 3.3.0), `contents: read` only, no `id-token`, no AWS-authenticating action of any kind. Neither slice moves this ADR's status to Accepted; that requires the OIDC trust to be applied and verified on real AWS, which slice 2A does not touch.** Status stays **Proposed**, not Accepted, until a real `terraform apply` and post-apply AWS verification confirm the OIDC provider and `enterprise-data-platform-shared-github-actions-role` actually exist as designed — matching this project's evidence-tier discipline (source existing is not deployment evidence). No GitHub Actions workflow file exists; no application/data stack was touched; `bootstrap/`'s and `logging/`'s own authentication behavior is unchanged. Exact GitHub repository this ADR's decision is scoped to: `DataEngAA/Enterprise_Data_Platform`. This ADR governs Phase 0's CI/CD Foundation workstream (`PROJECT_BLUEPRINT.md` §11, Step 9: "Create initial CI/CD foundation" — GitHub Actions validation, Terraform fmt, Terraform validate, security scan, plan generation, manual approval design for later production deployment). Full design detail: `02_Infrastructure/CI_CD.md`.

## Context

Phase 0's IAM foundation (ADR-0001), Logging and Audit Foundation (ADR-0002), Networking Hardening (ADR-0003), KMS and Secrets Foundation (ADR-0004), and Cost Controls (ADR-0005) workstreams are all complete and validated on real AWS. `PROJECT_BLUEPRINT.md` §11 Step 9 is next. Every Terraform stack in this project is currently applied by a human, on their own machine, after an MFA-authenticated login (`login.ps1`) — there is no automated validation, plan, or apply path today. This is not greenfield: the project already has an established, deliberately narrow trust model (one shared deployment role, trusted by exactly two principals, human-MFA and workstation-instance-profile) that any CI/CD design must extend without widening.

## Requirements

- No long-lived AWS access keys or secrets stored in GitHub — OIDC federation only.
- OIDC trust restricted to the exact GitHub repository (and branch/environment where relevant), not any repository or any ref.
- A dedicated, minimally privileged GitHub Actions IAM role, distinct from the existing shared deployment role, that reaches the deployment role via an explicit second `AssumeRole` hop rather than being granted the deployment role's own permissions directly.
- No path, at any hop, that lets GitHub Actions bypass the existing deployment role's already-reviewed permission boundary.
- `bootstrap/` (self-referential, defines the deployment role itself) gets CI validation and scanning, never automatic apply.
- `logging/`'s existing, considered human-direct authentication (ADR-0002 Option 3) is preserved, not silently routed behind the deployment role.
- Ordinary stacks (`kms-secrets/`, `cost-controls/`, `environments/dev`, future ingestion/processing stacks) support authenticated `terraform plan` in CI.
- PR workflow: format/init/validate/security-scan/plan for eligible stacks, never apply.
- Main/apply workflow: no blind automatic apply; a protected GitHub Environment with required manual approval; the plan is regenerated at deployment time, never reused from the PR.
- Plan artifacts are treated as potentially sensitive — no public raw `.tfplan`, redacted summaries instead, and the project's existing "never reuse a stale plan after a partial apply or state change" rule is preserved as a workflow property.
- Concurrency controls prevent two Terraform mutations racing against the same environment/stack.
- One primary IaC security scanner, chosen deliberately, not stacked without a concrete reason.
- No real AWS-specific value (account ID, ARN, repository identity) invented anywhere in this ADR or the accompanying design doc.

## Options Considered

**1. GitHub Actions authentication: OIDC federation vs. long-lived IAM user access keys stored as GitHub Secrets.**
Long-lived access keys were rejected outright — they are exactly the credential-management risk this project has avoided everywhere else (no permanent AWS keys on EC2, Secrets Manager/Parameter Store for anything that must exist, `08_Security/Security.md`'s standing rule against hardcoded secrets), and a leaked long-lived key has no natural expiry. **Decision: OIDC federation via `token.actions.githubusercontent.com`, per-run short-lived tokens, no stored AWS credential of any kind.** Full reasoning: `CI_CD.md` Section 3.

**2. Role chain shape: grant the GitHub Actions role the deployment role's own permissions directly vs. a single combined role vs. a dedicated, near-empty GitHub Actions role that hops to the existing deployment role via a second `AssumeRole`.**
Granting the GitHub Actions role its own copy of the deployment role's permissions was rejected — it would create two independently drifting permission sets doing the same job, doubling the audit surface for no benefit. A single combined role (GitHub OIDC trusts one role that *is* the deployment role) was rejected as the more serious problem: it would mean the deployment role's trust policy directly names an external, GitHub-controlled OIDC subject, collapsing the "who can reach infrastructure-management permissions" question into GitHub's own token-issuance correctness, with no intermediate identity a future security review could reason about independently. **Decision: a dedicated `enterprise-data-platform-shared-github-actions-role`, trusted only by the OIDC provider for this exact repository, whose only job is a conditioned second `sts:AssumeRole` call onto the existing deployment role** — structurally the same shape already accepted for the EC2 workstation role's own no-MFA trust statement. Full reasoning: `CI_CD.md` Sections 2 and 4.

**3. `bootstrap/` and `logging/` CI treatment: fold them into the same plan/apply-eligible stack list as everything else vs. give them validation-only CI participation with plan/apply permanently excluded.**
Including `bootstrap/` in the mutating-eligible list was rejected — it is the self-referential root of trust; a CI-triggered apply against it is a real privilege-escalation path (a compromised or misconfigured workflow could rewrite the trust boundary the entire chain depends on). Including `logging/` was rejected for a different, already-established reason: `ADR-0002` deliberately kept it outside the deployment role's reach, and reopening that boundary silently, as a side effect of a CI/CD design rather than a considered decision, would undo prior reasoning without a new ADR examining it. **Decision: both stacks participate in PR-time `fmt`/`validate`/security-scan (no AWS credentials needed for any of those three steps), and both are permanently excluded from CI-driven `plan` and `apply` — any real change to either continues through the existing human-direct, MFA-authenticated workflow.** Full reasoning: `CI_CD.md` Sections 5 and 6.

**4. Apply-time trust gating: rely on the OIDC `sub` claim's `ref:refs/heads/main` restriction alone vs. require a protected GitHub Environment with required-reviewer approval, gated by a `sub:...:environment:<name>` condition.**
Branch-only gating was rejected as insufficient for a mutating action — a push to `main` (even from a trusted contributor, even accidentally) would trigger an unattended apply with no human checkpoint, violating the explicit "no blind automatic apply" requirement. **Decision: apply jobs run only inside a protected GitHub Environment (proposed name `aws-dev`) with required reviewers; the OIDC trust policy's `sub` condition for the apply-capable pattern is scoped to that environment specifically, so a token capable of reaching the deployment role for a mutating action cannot exist until a human has clicked approve.** Full reasoning: `CI_CD.md` Section 8.

**5. Security scanner: Checkov alone vs. Checkov plus a second general-purpose scanner (e.g., Trivy, already used for this project's manual validation gates) vs. a different single tool.**
Stacking two Terraform-focused scanners was rejected without a concrete, identified gap — this project's own precedent (a single scanner, Trivy, for every manual validation gate to date, each finding individually reviewed and dispositioned) already established that one well-chosen tool with disciplined findings review is preferred here over redundant coverage for its own sake. Checkov was preferred over continuing with Trivy specifically for the CI context because it is IaC-native and Terraform-first, rather than a general vulnerability/config/secret scanner whose Terraform config-scanning mode this project has so far only used manually. **Decision: Checkov as the sole primary Terraform IaC scanner in CI; no second scanner added without a separately identified, concrete gap.** Full reasoning: `CI_CD.md` Section 12.

## Decision

Adopt the two-hop OIDC trust chain (GitHub OIDC -> `enterprise-data-platform-shared-github-actions-role` -> existing `enterprise-data-platform-shared-deployment-role`, unchanged in its own permission set) as this workstream's central architecture; restrict the OIDC trust policy's `sub` condition to this project's exact GitHub repository, using a branch-scoped pattern for read/plan-only jobs and an environment-scoped pattern (the protected `aws-dev` GitHub Environment) for the only jobs ever capable of reaching a mutating apply; exclude `bootstrap/` and `logging/` permanently from CI-driven plan/apply while including both in CI-driven validation and scanning; make `kms-secrets/`, `cost-controls/`, `environments/dev`, and future ingestion/processing stacks (subject to individual per-stack review) eligible for CI-authenticated plan on every PR and manual-approval-gated apply on merge to `main`; regenerate the Terraform plan at deployment time rather than reusing any PR-time plan, and never persist a raw `.tfplan` as a public or long-retained artifact, using redacted plan summaries for human review instead; enforce per-stack-and-environment GitHub Actions `concurrency` groups (`cancel-in-progress: false`) as a second, workflow-native layer on top of Terraform's existing S3 state locking; and adopt Checkov as the sole primary IaC security scanner for this workstream. Full detail: `02_Infrastructure/CI_CD.md`.

No AWS resource, IAM policy, or GitHub Actions workflow file is created by this ADR or its companion design document — both remain proposals pending review and the resolution of the seven unresolved decisions listed in `CI_CD.md` Section 15 (repository identity, repository visibility, `bootstrap/`-vs-dedicated-`cicd/`-stack placement of the OIDC provider and GitHub Actions role, one-vs-many apply workflow files, the real required-reviewer list, multi-environment role strategy, and Checkov version pinning).

## Benefits

Closes Phase 0's last purely-process gap (every other workstream has real AWS evidence; this one currently has zero automation) without introducing a single new standing credential anywhere — the entire design is credential-free until the moment a workflow run needs one, and even then the token is short-lived and scoped to one run. The two-hop chain and the `bootstrap`/`logging` exclusions demonstrate the same "know exactly what you're widening, and don't, without a reason" discipline this project has applied at every prior workstream's IAM decision, extended to an external, semi-automated caller for the first time — a meaningfully different threat model than any prior workstream has had to reason about, and a strong, realistic addition to this project's resume/interview value (`17_Interview_Guide/`) on OIDC federation, confused-deputy-style trust design, and CI/CD privilege boundaries.

## Costs

GitHub Actions minutes (free tier likely sufficient at this project's scale); Checkov itself is free and open-source; the OIDC identity provider and the new IAM role/policy carry no AWS charge. The main cost is design and review complexity — a two-hop trust chain, environment-gated approval, and a bootstrap/logging carve-out are more moving parts than a single "give CI the deployment role" shortcut would have been, a deliberate trade against that shortcut's much larger blast radius.

## Risks

Covered in full in `CI_CD.md` Section 14: public-repository/forked-PR execution, `pull_request_target` misuse, OIDC trust-condition drift toward over-broad `sub` matching, privilege escalation through `bootstrap/` if the exclusion in Section 5 were ever bypassed, stale-plan reuse, secrets/sensitive values leaking into Actions logs or artifacts, and racing concurrent Terraform operations. Each has a specific, structural mitigation in the design, not just a documentation note; none is fully eliminable by design alone (e.g., OIDC trust-condition drift is a review-discipline risk, not something Terraform can prevent on its own).

## Rejected Alternatives

Long-lived IAM user access keys as GitHub Secrets (Option 1); a single combined GitHub-OIDC-trusts-the-deployment-role-directly design, or granting the GitHub Actions role its own duplicate permission set (Option 2); including `bootstrap/`/`logging/` in the same plan/apply-eligible list as every other stack (Option 3); branch-only gating for apply with no protected-environment approval step (Option 4); a second, redundant IaC scanner alongside Checkov with no identified concrete gap (Option 5).

## Conditions for Reconsideration

- If `logging/` is ever deliberately reconsidered for deployment-role-routed authentication, that requires its own new ADR examining the original `ADR-0002` reasoning directly — not a silent change made as part of a future CI/CD refinement.
- If `bootstrap/`'s exclusion from CI apply is ever reconsidered, that is a fundamental re-architecture of this project's trust root and requires the highest level of scrutiny this project has applied to any decision to date, plus an explicit, separate ADR.
- If a second IaC scanner is later proposed, it must cite a specific, concrete gap Checkov's ruleset does not cover — not adopted as a default "more scanning is always better" addition.
- If the OIDC trust policy's `sub` condition is ever proposed to be widened (a broader `StringLike` pattern, a second repository, a wildcard ref), that requires a new ADR, not an inline trust-policy edit.
