- [ ] **Verify lock behavior** — confirm `use_lockfile = true` was honored (the `init` output/backend config confirms native S3 locking is in effect, consistent with `bootstrap`'s own already-verified locking configuration) — do **not** attempt a deliberate concurrent-lock contention test here; that remains explicitly deferred to `environments/dev`'s own eventual `apply` (`Terraform_Bootstrap_Design.md` §6, `PROJECT_EXECUTION_JOURNAL.md`'s repeated native-locking deferral notes), not this initialization step.

Answer nothing at that prompt; halt and get this reviewed before proceeding, since a wrong answer to a migration-style prompt can silently merge or discard state.

**Gate: `environments/dev` is initialized against its own, fresh, real S3 backend key, with no migration having occurred, before Section 5.**

## 6. Rollback and Stop Conditions

These apply throughout Sections 2–5, not only at the end. **Any one of the following halts work immediately** — do not attempt to "push through" or work around any of these within this checklist; each requires human review, and several require treating the situation as an incident rather than a routine correction.

- [ ] **Unexpected destroy** — any `plan` (Section 2 or Section 5) proposing to destroy a resource this checklist did not anticipate destroying (which, per this checklist, is: nothing — no step in this checklist should ever propose a destroy).
- [ ] **Replacement of bootstrap resources** — any proposed replacement (not just change) of `aws_s3_bucket.terraform_state`, any of its hardening sub-resources, or `aws_iam_role.deployment` itself, in any plan run as part of this checklist.
- [ ] **Trust-policy change** — any diff to `aws_iam_role.deployment`'s `assume_role_policy`, detected either in a `plan` (Section 2) or in the post-apply AWS-side check (Section 3). This checklist does not implement Bootstrap Update 2 (the trust-policy addition for the future workstation role) — any trust-policy diff at all, at this stage, is unexpected and out of scope.
- [ ] **Bootstrap state-bucket modification** — any proposed or applied change to the state bucket's versioning, encryption, Block Public Access, ownership controls, or bucket policy, at any point in this checklist. Bootstrap Update 1 is IAM-policy-only; the bucket should never appear as anything other than an unchanged data source (if referenced at all) in any plan here.
- [ ] **Broad IAM permissions** — any statement in any of the three managed policy documents, `aws_iam_policy.deployment_dev_permissions` (10 statements), `aws_iam_policy.deployment_dev_networking_permissions` (12 statements), or `aws_iam_policy.deployment_dev_workstation_iam_permissions` (4 statements) (as any actually appears in a `plan` or, worse, as actually attached in Section 3's verification), that grants `"Action": "*"`, `"Resource": "*"` with no condition, `iam:*`, `AdministratorAccess`, or any action/resource combination broader than what `bootstrap/main.tf`'s already-reviewed 26 statements (across all three documents) define. If any applied policy does not match its reviewed source exactly, treat this as an incident, not a routine finding.
- [ ] **IAM policy size quota exceeded** — **UPDATED 2026-07-26 (second occurrence, this time caught entirely at plan time)**: this happened twice for real. First, `CreatePolicyVersion: LimitExceeded: Cannot exceed quota for PolicySize: 6144` against the pre-split single combined policy (no AWS change resulted, since the failed call left the prior default policy version active) — the direct trigger for the two-policy split. Second, `aws_iam_policy.deployment_dev_permissions`'s own `lifecycle.precondition` reported its rendered JSON at 6212 characters, 68 over quota, after the two-policy split — caught entirely at `plan` time, no AWS API call involved at all — the direct trigger for the workstation-IAM policy split into a third policy. Going forward, watch for any of the three policies' `lifecycle.precondition` failing during `plan` (Section 2's "Policy size check"), or a raw `CreatePolicyVersion`/`CreatePolicy` size error surfacing despite a passing precondition (which would itself indicate a precondition's Terraform-computed length and AWS's real count have diverged — worth investigating, not dismissing). Do not respond to either by silently dropping a condition or tag requirement to shrink a document, and do not respond by merging any of the three policies back together — treat any recurrence as a stop condition requiring a further, separately reviewed structural change (e.g., a fourth policy).
- [ ] **Unexpected public ingress** — any security-group rule, anywhere in any plan run as part of this checklist, that opens inbound access from `0.0.0.0/0` or `::/0` on any port, to any resource.
- [ ] **Backend migration prompt** — any interactive prompt suggesting Terraform wants to migrate or copy state between backends, at any point in Section 3 (re-running bootstrap commands) or Section 4 (dev's first init) — per Section 4's own note, no legitimate migration should ever be expected for `environments/dev`'s first-ever initialization.
- [ ] **Provider authentication failure** — any `AssumeRole`-related error (access denied, invalid principal, expired MFA session) during Section 3's apply or Section 4/5's provider-level `assume_role` (`providers.tf`). Do not retry with broadened permissions or a different identity as a workaround — diagnose why the expected identity/trust/permission combination failed, per `Terraform_Bootstrap_Break_Glass_Procedure.md` if the diagnosis points to a genuine access problem rather than a simple expired-session retry. **Real occurrence, 2026-07-26 (SEVENTH STATUS UPDATE above)**: a self-assume `AccessDenied` recurred when ambient shell credentials were already an assumed deployment-role session and `providers.tf`'s own `assume_role` block tried to assume the same role again — resolved not by removing that block but by starting from a fresh base-IAM-user MFA session via `login.ps1` before running any Terraform command. Before assuming a fresh `provider`/`assume_role` failure is a new issue, first check `aws sts get-caller-identity` for exactly this pattern (an `assumed-role/<deployment-role-name>/*` ARN already present before Terraform runs).
- [ ] **State-lock issue** — a `.tflock`-related error (failure to acquire, or an unexpectedly already-locked state) during Section 3 (bootstrap) or Section 4/5 (`environments/dev`). Per `README.md` "State Safety" and the break-glass procedure: diagnose (confirm no other real Terraform process is actually running) before ever considering `force-unlock` or manual lock-object deletion — never a first response.
- [ ] **Any AWS resource outside approved scope** — any resource type appearing in any plan in this checklist that is not one of: the two Bootstrap Update 1 IAM resources (Section 2/3), or the VPC/subnet/IGW/route-table/security-group/workstation-role/instance-profile/EC2-instance set explicitly enumerated in Section 5. An unrecognized resource type appearing anywhere is a stop condition regardless of how small or apparently harmless it looks.

**On any stop condition:** do not attempt further Terraform commands against the affected configuration. Record what was seen (command, output, which stop condition matched) for review, consistent with this project's evidence discipline — a stop condition is itself a real, reportable event, not something to quietly retry until it goes away.
