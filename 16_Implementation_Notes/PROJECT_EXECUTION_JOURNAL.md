# Project Execution Journal

This journal is a sanitized, public-facing record of how this project's AWS foundation (Terraform bootstrap and the `environments/dev` stack) was actually built: milestones, architecture decisions, problems encountered, root-cause investigations, fixes applied, and validation results. It is derived from a more detailed private engineering log and has been edited for public sharing — informal language has been rewritten in professional terms, and all account-specific identifiers (account IDs, ARNs, bucket names, IP ranges beyond the project's own internal addressing scheme) have been replaced with placeholders or omitted. No technical finding, failure, or fix has been removed for the sake of appearances; the intent is to preserve engineering judgment and traceability while protecting private account details.

Evidence in this journal is described honestly by what was actually verified at each point — a design decision, a piece of code that exists, a static review finding, a real `terraform validate`/`plan`/`apply` result, or a real AWS CLI confirmation — rather than assumed complete because a prior step succeeded.

---

## 1. Project Summary

An Enterprise AWS Data Engineering Platform, built to demonstrate real infrastructure and data engineering practice: ingestion, storage (Landing → Bronze → Silver → Gold), processing, and serving layers on AWS, backed by Terraform-managed infrastructure. This journal covers the **Pre-Phase / Engineering Environment Setup** stage: AWS account preparation, the Terraform state/IAM bootstrap, and the first development (`dev`) environment — a single EC2 development workstation on a dedicated VPC, managed entirely through Terraform.

## 2. Architecture and Design Decisions

- **Region:** a single AWS region was selected for the project and used consistently across all environments.
- **State management:** Terraform state is stored remotely in a dedicated, versioned, encrypted S3 bucket, with native S3 locking (`use_lockfile`) rather than a separate DynamoDB lock table — chosen for simplicity and lower operational overhead at this project's scale.
- **IAM model:** a single shared Terraform **deployment role** performs all `environments/dev` infrastructure changes. The human operator authenticates as an IAM user with MFA and assumes the deployment role for each Terraform run; the deployment role itself is never assumed from within an already-assumed session (see Section 8 for why this matters).
- **Bootstrap sequencing:** the state bucket and deployment role are created first, using local Terraform state (since no remote backend can exist before the bucket that would host it). State is migrated into the new S3 backend once the bucket is verified.
- **Least privilege:** the deployment role starts with no permissions attached. Permissions are added incrementally, in reviewed, narrowly-scoped IAM policy documents, only as specific infrastructure work requires them — not granted broadly upfront.
- **Networking:** a dedicated VPC with a single public subnet is used for the `dev` workstation. No NAT Gateway, no private subnets are deployed yet (reserved CIDR ranges exist in design documentation for future tiers). The workstation's security group has zero inbound rules; access is exclusively via AWS Systems Manager Session Manager, not SSH.
- **Compute:** a single EC2 instance (Amazon Linux 2023, x86_64) serves as the development workstation, with an encrypted `gp3` root volume, IMDSv2 enforced, and a version-controlled, idempotent bootstrap script for tooling installation.
- **Disposability:** the `environments/dev` workstation is treated as disposable and reproducible from Terraform — unlike the bootstrap state bucket and deployment role, it does not carry `prevent_destroy`.

Full design rationale for each of these decisions is in `02_Infrastructure/Terraform_Bootstrap_Design.md`, `02_Infrastructure/EC2_Development_Workstation.md`, and `16_Implementation_Notes/Dev_Environment_Terraform_Implementation_Plan.md`.

## 3. Bootstrap Implementation

The Terraform bootstrap stack (`infrastructure/terraform/bootstrap/`) creates and hardens the S3 state bucket (versioning, SSE-S3 encryption, Block Public Access, `BucketOwnerEnforced` ownership, a TLS-only bucket policy) and the shared deployment IAM role (trust policy scoped to the human operator's IAM user, gated on an active MFA session).

Implementation went through two static-review passes before any Terraform command was run, correcting: an outdated AWS provider version constraint; a no-op encryption setting; an overly broad IAM-principal trust condition (narrowed to IAM-user ARNs only); a missing account-ID safety check on the provider (`allowed_account_ids`); and an initial, over-broad state-access permission set that was rewritten to grant only the exact object and lock-object operations required. A subsequent review further narrowed the deployment role's own management model: rather than attaching any permissions to the role during bootstrap, the role was left with a trust policy only, with all infrastructure permissions added in a later, separately reviewed step ("Bootstrap Update 1," Section 5).

**Validation performed on the bootstrap stack**, in order: `terraform fmt`, `terraform init` (local state), `terraform validate` — all passed. TFLint found and a fix resolved one unused-variable warning; a rerun confirmed zero findings. A Trivy configuration scan found two findings, both reviewed and accepted as deliberate design trade-offs for this project's scale rather than fixed: S3 access logging left disabled (would require a separate hardened log-destination bucket, deferred), and SSE-S3 encryption used instead of a customer-managed KMS key (avoids key-policy complexity and bootstrap-lockout risk; SSE-S3 still provides encryption at rest). Neither finding was suppressed — both are documented, reviewed, accepted trade-offs.

`terraform plan` then proposed exactly the seven expected resources with no unexpected diff. `terraform apply` succeeded, and the resulting state bucket and deployment role were independently verified against real AWS API output (`aws s3api get-bucket-versioning`/`get-bucket-encryption`/`get-public-access-block`/`get-bucket-policy`, `aws iam get-role`/`list-attached-role-policies`) — confirming every hardening control matched the design.

State was then migrated from local to the new S3 backend (`terraform init -migrate-state`), verified via `terraform state list`, a no-diff `terraform plan`, and a direct `aws s3api head-object` check on the remote state object. Native S3 locking was exercised passively (every backend operation since migration succeeded without error) rather than deliberately load-tested at this stage — a genuine concurrent-lock contention test was deferred to the longer-running `environments/dev` apply, which provides a more natural test window. Local state files and a temporary migration backup were deleted only after remote-state readability was independently confirmed multiple times.

## 4. `environments/dev` Design and Implementation

A full implementation plan (`16_Implementation_Notes/Dev_Environment_Terraform_Implementation_Plan.md`) was written and reviewed before any code was created, covering module boundaries, the exact deployment-role IAM policy needed, VPC/subnet CIDR allocation, AMI selection strategy, instance sizing, IMDSv2 configuration, and the bootstrap script's approved scope. Three internal documentation conflicts were identified during this review and resolved explicitly (state-key granularity, networking design-phase scope, and a stale IAM role-naming example), rather than silently reconciled.

The resulting Terraform source consists of three reusable modules — `modules/vpc`, `modules/iam-workstation-role`, `modules/ec2-workstation` — composed by a single root module, `environments/dev/`, plus a version-controlled bootstrap script (`scripts/bootstrap_workstation.sh`) for baseline tooling installation (git, GitHub CLI, `uv`) on the workstation. The script deliberately never handles credentials, never clones a repository, and never runs Terraform itself — those remain manual, interactive steps performed by the developer after connecting to the instance.

**Validation on `environments/dev` and its modules**: `terraform fmt` and `terraform validate` passed across all five directories (bootstrap, `environments/dev`, and the three modules). An initial TFLint run found nine warnings (two unused reserved-CIDR variables, one unused module input, and six missing version-constraint declarations across the three modules); all were fixed in source, and a rerun confirmed zero findings. A Trivy scan found five additional findings across both stacks — an `iam:PassRole` grant (reviewed and accepted after confirming it is scoped to an exact role ARN with a service-restriction condition, not a wildcard), unrestricted security-group egress (accepted as a temporary, explicitly risk-accepted trade-off for this development phase — inbound access remains fully blocked, which is this design's primary control), and VPC Flow Logs left disabled (accepted as a deferred control for a single, disposable development instance). None of the findings were suppressed; all were reviewed and documented.

## 5. Deployment-Role Permission Corrections ("Bootstrap Update 1")

Granting the deployment role permission to manage `environments/dev` resources required several rounds of correction, each triggered by a real finding rather than assumed correct from source review alone:

1. **RunInstances condition-key scoping.** An initial statement applied an `ec2:Owner` condition across a resource list mixing an AMI resource type with several non-AMI resource types. `ec2:Owner` is only meaningful for the AMI a launch references — the statement was split into an AMI-specific statement and a separate statement for the other resource types created by the same `RunInstances` call.
2. **A real, partial `apply` failure** revealed a missing `ec2:DescribeVpcAttribute` permission needed while Terraform waited for a VPC attribute update to complete — added to the existing read-only statement.
3. **A second real, partial `apply` failure** revealed that a networking-resource-creation statement's tag-enforcement condition had no value for the *existing* parent VPC referenced by some multi-resource-type actions (`CreateSubnet`, `CreateRouteTable`, `CreateSecurityGroup` each authorize against both a new resource and an existing VPC). The statement was split into paired new-resource/existing-resource conditions, confirmed against AWS's own IAM condition-key reference documentation.
4. **A tag-enforcement bypass** was found on review: an unconditioned statement granting the same networking-create actions coexisted alongside a tag-conditioned statement granting the identical actions — since IAM `Allow` statements are additive, the untagged grant made the tag requirement unenforceable. Corrected by removing the untagged statement so only the tag-conditioned grant remains.
5. **Two real IAM managed-policy size-quota failures** (AWS enforces a size limit on a single customer-managed policy document) — the first surfaced as a real `iam:CreatePolicyVersion` API rejection with no resulting AWS-side change; the second was caught earlier, entirely at `terraform plan` time, by a `lifecycle.precondition` added specifically to measure the real, Terraform-rendered policy size against the quota. Both were resolved by splitting the deployment role's permissions across three purpose-scoped managed policies (core deployment/state access, networking, workstation-IAM management) rather than one oversized document.
6. **A forced-replacement defect**, caught in a human-reviewed `terraform plan` before any apply: a policy's `description` argument is immutable in AWS IAM (`Forces new resource` in the provider), and two prior corrections had rewritten it, silently queuing an unwanted replacement of an already-live, in-use policy. Fixed by resetting the description to a stable string and adding `lifecycle.ignore_changes` for that argument on all three policies, permanently closing off this class of mistake.
7. **A real, partially destructive apply**: after the fixes above, an apply run detached and deleted a live policy, created two new ones, then failed to recreate the first with a real AWS validation error — its description exceeded IAM's absolute character limit. Corrected by shortening all three policies' descriptions to short, stable strings well under the limit.

Following these corrections, a real `terraform apply` completed successfully, and an independent, subsequent `terraform plan` reported no differences between configuration and deployed state — the strongest evidence obtained for this policy: not just that an apply succeeded, but that a separate, later read of real AWS state confirms it still matches.

## 6. `environments/dev` Deployment History

Two real `terraform apply` attempts against `environments/dev` partially succeeded before failing on the permission gaps described in Section 5 items 2–3, leaving a VPC, an Internet Gateway, and the workstation IAM role/instance profile/attachment already created in AWS before each stop. No manual cleanup, state manipulation, or resource import was performed in response — each recovery instead followed a fixed sequence: validate the corrected bootstrap source, re-plan and re-apply the bootstrap policy, then return to `environments/dev` for a fresh (never reused) plan, reviewing whether the partially created resources reconciled cleanly or required a further change.

## 7. `DevRunInstancesAmi` Authorization Investigation

After the deployment role's permissions were stabilized (Section 5), `RunInstances` calls continued to be denied specifically against the AMI resource, despite the relevant IAM statement appearing correct on review. This prompted a structured, one-variable-at-a-time diagnostic investigation: each of the statement's three conditions (region restriction, AMI-owner restriction, instance-type restriction) was temporarily removed in turn, with real AWS authorization-decoding and policy-simulation output reviewed after each change. None of the removals changed the observed failure.

Two claims raised during this investigation — that no attached policy grants EC2 compute permissions at all, and that the deployment role has no access to the Terraform state bucket or its lock object — were checked directly against the actual, current policy source before any new policy was created in response. Both claims were found to be incorrect: the relevant permissions were already present. No duplicate or redundant policy was created.

**Root cause:** the investigation's premise was wrong. Terraform had not, in fact, been operating under a genuine, fully authenticated deployment-role session throughout this period — a stale or incomplete MFA/STS credential state meant the role assumption Terraform believed it had performed was not actually in effect. Once a fresh, correctly authenticated session was established, `RunInstances` succeeded even with the AMI statement's conditions still stripped down for diagnostics, conclusively ruling out the IAM condition content as the actual blocker.

Separately, a genuine, account-level EC2 launch restriction (unrelated to IAM) rejected the project's default instance type at launch time; manual testing identified an alternative instance type that launches successfully in this account. Rather than change the project's approved default sizing everywhere, a narrowly scoped, explicitly temporary allow-list addition was made in the three places instance-type validation is enforced, with the approved default left unchanged and an explicit condition recorded for when the addition should be reverted.

The AMI-statement conditions were then restored to their originally designed values, with the temporary instance-type addition included for consistency with the workaround above.

**Correction to this investigation's conclusion, made the same day, before this journal was prepared for publication:** a subsequent `terraform plan`/`apply` run from the `environments/dev` stack reported no differences and no changes applied. This result was initially, incorrectly, treated as confirmation that the restored AMI-statement conditions had been deployed. It does not confirm that. `environments/dev` and the bootstrap stack are separate Terraform root modules with separate state — a plan or apply run from `environments/dev` never reads or applies anything in the bootstrap stack's configuration, and cannot confirm what IAM policy content is actually live in AWS. The corrected, accurate status is:

> **Authentication root cause resolved. Existing dev infrastructure validated. Bootstrap IAM-condition deployment and future-launch authorization validation remain pending.**

**Verified:** the MFA-backed authentication workflow works correctly; stale session credentials are cleared before each new session; Terraform authenticates through the IAM user's MFA session and successfully performs its own role assumption; the existing `environments/dev` infrastructure matches its Terraform state and configuration; the most recent `environments/dev` plan/apply completed with no resources added, changed, or destroyed.

**Not yet verified:** whether the restored bootstrap IAM policy conditions have actually been applied to AWS; whether the currently deployed deployment-role policy contains all three restored conditions; whether a genuinely new, permitted `RunInstances` request succeeds under those conditions; whether the temporary instance-type workaround can be reverted once the underlying account restriction is resolved.

**Required next steps before this investigation is closed:**
1. Authenticate using the project's MFA login workflow.
2. Run `terraform plan` against the **bootstrap** stack specifically (not `environments/dev`).
3. Review and apply any IAM policy changes that plan proposes.
4. Confirm via a direct read of the deployed policy (`aws iam get-policy-version`) that it contains the region restriction, the AMI-owner restriction, and the approved instance-type values.
5. Perform a safe authorization check via IAM policy simulation, or an explicitly approved, controlled resource test — not an ordinary `environments/dev` plan/apply, which does not exercise the bootstrap-managed policy.
6. Do not replace or destroy the existing workstation to test this without explicit approval.

## 8. Self-Assume-Role Authentication Failure

Separately from Section 7, a `terraform apply` run on a later day failed immediately with an `AssumeRole` access-denied error, before reaching any resource. The cause: the active shell session already held temporary credentials for an *already-assumed* deployment-role session (left over from earlier manual diagnostic work), and Terraform's own provider configuration then attempted to assume the same role a second time from within that session. AWS IAM's role-trust evaluation treats an assumed-role session as a different kind of principal from the underlying IAM user — the deployment role's trust policy, which trusts only the IAM user (with an MFA condition), does not recognize an assumed-role session as a valid caller, so the second assumption is denied.

This was diagnosed against the real trust-policy source rather than worked around by removing the provider's role-assumption configuration (which would have broken the intended, general authentication pattern). The existing project authentication script was reviewed and confirmed to already implement the correct behavior: it clears any stale session-credential environment variables before requesting a new session, authenticates using a fresh MFA-backed session token (not a role assumption) so the resulting identity is always the base IAM user, stops immediately on any AWS CLI failure without reporting success, and only confirms success after an independent identity check. No script change was required.

**Standing workflow for all Terraform commands in either stack:** authenticate via the MFA login script → confirm the resulting identity is the base IAM user, not an already-assumed role → change into the relevant stack directory → `terraform plan` → `terraform apply`. A deployment-role session should never be manually assumed ahead of time; the Terraform provider's own configuration performs that single step.

## 9. Lessons Learned

- **A first correction is not always the last one needed.** Several IAM findings in this project were only surfaced by a subsequent, real `apply` or `plan`, not by static review alone — static review is necessary but not sufficient for catching resource-type-scoping and multi-statement interaction defects in IAM policy.
- **A scanner or linter finding is a fact to triage, not a verdict to obey.** Every Trivy/TFLint finding in this project was reviewed against actual context before being fixed or explicitly accepted as a documented trade-off — none was fixed reflexively, and none was silently ignored.
- **A superficially identical failure signature can have entirely different causes.** Repeated `UnauthorizedOperation`/authorization-denial errors against the same IAM statement were, at different points in this project, caused by a genuine content defect, and later by an authentication/session problem entirely outside the policy document itself. Distinguishing the two required live, real AWS evidence (decoded authorization failures, policy simulation), not just re-reading the source.
- **A no-op Terraform result only proves what it actually touched.** A `plan`/`apply` reporting no changes is strong evidence for the specific Terraform root module it ran against — it is not evidence for a different, separately-stated stack, even when both stacks are logically related. This project initially conflated the two and corrected the record once the distinction was identified.
- **Verification-before-action prevents redundant infrastructure.** Multiple claims of "missing" permissions during this project's IAM debugging were checked directly against the current, real policy source before any new policy was created in response — in every case, the claimed gap did not exist, and no duplicate policy was ever created.
- **Documentation that overclaims is a liability.** Every correction recorded in this journal exists because a later, more careful review caught language that stated more certainty than the available evidence actually supported.
