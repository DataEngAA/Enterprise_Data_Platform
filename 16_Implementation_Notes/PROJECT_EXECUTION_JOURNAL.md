## 1. Journal Purpose and Usage

This journal exists so that the full engineering process — not just the current clean design — can be understood, resumed, or repeated later, by the same person or someone else. It is written for five concrete uses:

- **Restarting after a long break.** Read Sections 3-27 in order to reconstruct why every current decision exists, then go straight to Section 28 (immediate next task) and Section 34 (resume checklist).
- **Rebuilding the same project from scratch.** Sections 4-14 give the design reasoning; Section 33 lists exactly which files carry that design; Section 32 gives the exact commands, in order, that took the code from written-but-unrun to validated/linted/scanned.
- **Interview preparation.** Section 26 (AI-assisted workflow) and Section 31 (mistakes and corrections index) are written specifically to support an honest, concrete account of how this project was actually built — see also `17_Interview_Guide/Phase_0.md` Sections 31-41 (Q58-Q101), which turn this same material into rehearsed question/answer form.
- **Troubleshooting.** Section 15 (the Cowork tooling blocker) and Section 21 (the TFLint unused-variable finding) are worked examples of how a real blocker was diagnosed and resolved without guessing or suppressing evidence — the same discipline described generally in `16_Implementation_Notes/Terraform_Bootstrap_Break_Glass_Procedure.md`.
- **Explaining why the final design differs from the first draft.** Sections 11-14 exist specifically to show the reasoning trail from an initial, more permissive draft (a narrowly-scoped placeholder IAM policy on the deployment role) to the final, more conservative design (zero permissions on that role) — a decision that only makes sense with the intermediate steps visible, not just the end state.

This journal is a supplement to, not a replacement for, the authoritative design/status documents it references throughout (`02_Infrastructure/Terraform_Bootstrap_Design.md`, `16_Implementation_Notes/Terraform_Bootstrap_Implementation_Plan.md`, `infrastructure/terraform/bootstrap/README.md`, `00_Project_Management/Memory.md`, `16_Implementation_Notes/Bootstrap_Checklist.md`). Where this journal and any of those documents ever appear to disagree, the dated, narrower document wins for *current state*; this journal wins for *how we got here*.

## 2. Evidence-Status Legend

Every claim in this journal, and in the project generally, sits at one of seven evidence tiers (first formalized in `17_Interview_Guide/Phase_0.md` Q63). This journal uses these exact labels throughout — nothing is described as a stronger tier than it has actually reached:

| Tier | Label used in this journal | What it proves | What it does NOT prove |
|---|---|---|---|
| 1 | **Design evidence** | A design was written and reviewed/approved by the user. | That anything was built. |
| 2 | **Code-created evidence** | Files were written matching an approved design. | That the code is correct or runs. |
| 3 | **Static-review evidence** | A human read the created code and found/fixed real issues. | That the code executes. |
| 4 | **Validation evidence** | `terraform fmt`/`init`/`validate` (and tools like TFLint/Trivy) were actually run and the relevant check passed. | That `plan`/`apply` will succeed, or anything about real AWS behavior. |
| 5 | **Plan evidence** | `terraform plan` was actually run and reviewed. | That `apply` will succeed or that resources exist. |
| 6 | **Deployment evidence** | `terraform apply` was actually run against real AWS and resources were actually created. | That those resources are correctly hardened. |
| 7 | **Operational-verification evidence** | Real `aws` CLI output (or an actual drill) confirms deployed resources/procedures behave as designed. | Nothing further — this is the top tier. |

**As of this entry, this project has tiers 1-4 for the bootstrap Terraform code, and tier 1 (design only) for the break-glass procedure.** Tiers 5-7 do not exist for anything in this project yet. Any sentence in this journal describing something at tier 5 or above would be an overclaim; none is made. Two additional flat labels are used throughout, per this project's standing rules (`CLAUDE.md` Section 2.10):

- **"Validation evidence pending"** — the claim depends on a command or drill that has not yet been run.
- **"Implementation evidence pending"** — the claim depends on an AWS resource that does not yet exist.

## 5. Networking and EC2 Workstation Design Decisions

**Evidence tier: design evidence (approved 2026-07-24), zero implementation evidence.**

- **Public development subnet** inside the dedicated VPC, with an Internet Gateway and public IPv4 on the instance.
- **Zero inbound security-group rules** — the public IP controls routability only; actual reachability is fully governed by the security group, which permits nothing inbound.
- **Session Manager only** for administrative access — port 22 is never opened, under any circumstance.
- **No NAT Gateway** for the initial workstation — outbound reachability comes from the IGW + public IP model; private-subnet + NAT/VPC-endpoints is documented as a future hardening option only, not built now.
- **Amazon Linux 2023, x86_64** (superseding an earlier ARM64/Graviton draft recommendation, flagged rather than silently overwritten — see `EC2_Development_Workstation.md`).
- **Instance sizing:** `t3.medium` default, `t3.large` for temporary heavier work, `t3.xlarge` for exceptional short bursts only (not a size to leave running).
- **Storage:** 30 GiB encrypted `gp3` root volume.
- Manual shutdown discipline now; scheduled automatic shutdown deferred to later, once real usage patterns are observed.
- Decisions recorded in `02_Infrastructure/EC2_Development_Workstation.md`, `02_Infrastructure/AWS_Account_Preparation.md`.

## 8. Terraform Bootstrap Architecture

**Evidence tier: design evidence, reviewed and approved by the user (2026-07-24).**

Full detail lives in `02_Infrastructure/Terraform_Bootstrap_Design.md`; the key approved decisions, adopted as project facts throughout everything that follows:

- **Bootstrap chicken-and-egg problem** resolved by running the very first apply with **local Terraform state**, then migrating that local state into a newly-created S3 backend once the bucket exists.
- **Native S3 state locking** (`use_lockfile = true`, requires Terraform >= 1.10) chosen over the traditional S3+DynamoDB pattern — simpler, cheaper (this account is not Free Tier eligible, so DynamoDB would be a small but non-zero recurring cost), and a smaller operational surface, accepting a shorter track record as the trade-off. **No DynamoDB table is created.**
- **SSE-S3 (`AES256`)** for state-bucket encryption, not SSE-KMS, during bootstrap — no customer-managed KMS key. Revisit only if a clear security/governance requirement emerges later.
- **Bootstrap runs manually from the human identity's own laptop/CloudShell** — the EC2 workstation is explicitly not required to exist first.
- **The Terraform deployment role is created by the bootstrap Terraform config itself** (not clicked through the Console), trust policy initially scoped to the human identity only, later updated (a separate, future, reviewed change) to also trust the workstation role once it exists.
- **Deployment-role max session duration: 1 hour** (3600 seconds), not the 12-hour default.
- **The existing, manually-created AWS Budget is explicitly NOT imported into Terraform** — recorded as a deliberately manually-managed exception.
- **VPC design reserves CIDR space** for public/private-application/private-data subnet tiers, but only the public tier is deployed now; no NAT Gateway.
- **Break-glass protection required in principle** (`prevent_destroy`, no delete permission on the deployment role, versioning, Block Public Access, TLS-only policy, least privilege, documented recovery/import) — approved as a mandatory design requirement, with the exact break-glass procedure itself deferred to a later, separate task (resolved in Section 24).
- Only `dev` is planned as the first deployed environment; `test`/`stage`/`prod` are not scaffolded until their own implementation phase begins.

## 9. Terraform Bootstrap Implementation Planning

**Evidence tier: design/planning evidence. Two drafts existed — the first was revised before anything was created.**

A first-draft implementation plan proposed `bootstrap/` composed of two separate modules, `modules/state-backend` and `modules/iam-deployment-role`, plus a forward-looking `environments/dev/` design using four additional modules. **This draft was superseded before any code was written** — the user's final decision narrowed scope explicitly:

- **No modules at all for this scope.** All bootstrap resources (state bucket + hardening + the deployment IAM role) are defined **directly in `bootstrap/main.tf`**. `modules/state-backend` and `modules/iam-deployment-role` were not deferred — they were removed from the plan entirely, not "later if needed."
- `modules/security-group` was also dropped as a standalone module; the workstation security group is folded into `modules/ec2-workstation` instead (for the still-not-created future `environments/dev/` work).
- **`Environment = shared`** adopted as a resource-scope tag value for account-level, project-wide bootstrap resources — explicitly *not* a fifth deployment environment (`dev`/`test`/`stage`/`prod` remain the only four). This was recorded in `01_Architecture/Naming_Convention.md`, which also corrected an earlier, incorrect deployment-role naming example (`enterprise-data-platform-dev-deployment-role` → `enterprise-data-platform-shared-deployment-role`).
- `backend.tf` was decided to be **present in the file tree from the start**, with its `s3` backend block written but commented out (a two-phase file), rather than added only later at migration time.
- Exact Terraform/AWS-provider versions were deliberately left to be verified immediately before code creation, not fixed in the plan.
- The final, approved plan is `16_Implementation_Notes/Terraform_Bootstrap_Implementation_Plan.md`.

This is the first concrete example, in this project's own history, of a first draft being revised toward a narrower, more conservative design before implementation — the same pattern recurs more consequentially in Sections 11-14.

## 12. Issues Discovered During Static Review

Nine issues, found in the first pass:

1. **Outdated AWS provider major-version constraint** — the `>= 5.0.0, < 6.0.0` floor was no longer current.
2. **`bucket_key_enabled` present in the SSE-S3 encryption block** — a no-op setting, since S3 Bucket Keys only reduce cost/traffic for SSE-**KMS**-encrypted objects, and this bucket uses SSE-S3.
3. **`human_bootstrap_principal_arn` validation too broad** — its description implied IAM Identity Center / STS assumed-role support that the trust-policy design, as written, does not actually support (an assumed-role session's effective principal ARN does not match a static IAM user ARN).
4. **No protection against running against the wrong AWS account** — nothing checked that the active credentials matched the account this configuration was scoped for.
5. **No dedicated variable for the bootstrap state key**, and the deployment role's IAM permissions were not yet precisely scoped to it.
6. **The deployment-role permission policy was a blanket `bucket/*` grant** (including `DeleteObject`), far wider than needed — a leftover from the placeholder policy created in Section 10.
7. **Tag-merge ordering bug** — `locals.tf` merged in an order that would let a caller-supplied `additional_tags` value silently override a required tag (e.g., `Owner`).
8. **`backend.hcl.example` was missing `encrypt = true`.**
9. **Documentation gaps** — prerequisites/required-inputs sections didn't yet mention the new account-safety variable, and the "unresolved permission scope" explanation needed rewriting once the policy was rescoped.

## 13. Corrections Applied (First Pass)

All nine issues above were corrected in the same review pass, with no `terraform` command run to do so:

1. `versions.tf`: AWS provider constraint corrected to `>= 6.0.0, < 7.0.0`.
2. `main.tf`: removed `bucket_key_enabled` from the SSE-S3 block.
3. `variables.tf`: `human_bootstrap_principal_arn` validation narrowed via regex to IAM-user ARNs only (`arn:aws:iam::<account-id>:user/<name>`); description rewritten to state Identity Center/STS assumed-role support is deferred to a future, separate trust-policy design, not silently assumed to work.
4. Added a required `aws_account_id` variable (validated as exactly 12 digits, no default), wired into `providers.tf` as `allowed_account_ids = [var.aws_account_id]`.
5. Added a `bootstrap_state_key` variable (default `bootstrap/terraform.tfstate`) — **this variable was later removed entirely once it became unused, see Section 21.**
6. Rewrote the deployment-role permission policy from the blanket grant to four precisely-scoped statements: `ListBucket` conditioned on `s3:prefix`, bucket-metadata reads, `GetObject`/`PutObject` (no delete) on the exact state object, and `GetObject`/`PutObject`/`DeleteObject` only on the exact `.tflock` lock object.
7. `locals.tf`: merge order reversed to `merge(var.additional_tags, {required tags...})` so required tags always win.
8. `backend.hcl.example`: added `encrypt = true`.
9. `README.md`: updated prerequisites/required inputs, rewrote "Unresolved Permission Scope" to reflect the new exact-object scoping, marked `terraform import` guidance as illustrative.

**Evidence obtained: static-review evidence (tier 3).** No `terraform` command was run; `.terraform.lock.hcl` did not exist; no AWS CLI command was run; no AWS resource was created.

## 14. Final Bootstrap-Management-Model Decision

### Step
- **Goal:** A second, final static-review pass before moving to any real command execution.
- **Action:** Re-read all ten files plus the design/plan/status documents again.
- **Decision — the most consequential correction in this project's history so far:** the item-6 fix in Section 13 (narrowing the deployment role's S3 permissions) was itself revisited and found to be solving the wrong problem. The real question wasn't "how narrowly should the deployment role's access to bootstrap's own state be scoped" — it was **"should the deployment role have access to bootstrap's own state at all?"** The answer adopted: **no.** This bootstrap root module remains a **human-administered exception** — its provider/backend run as the human identity directly, with no `assume_role`, permanently, not just during the initial chicken-and-egg window. The Terraform deployment role's actual job is to **later** manage `environments/dev`, not this bootstrap configuration's own state. Granting it access to `bootstrap/terraform.tfstate` — however narrowly scoped — would let a role whose job is managing dev infrastructure also read/write the very state object that defines the deployment role itself and the state bucket's hardening: a self-referential, unnecessary expansion of blast radius.
- **Result:** `aws_iam_policy.deployment_permissions`, `aws_iam_role_policy_attachment.deployment_permissions`, and their policy document were **removed entirely** from `main.tf` — not narrowed further. `aws_iam_role.deployment` is kept (its name/ARN/trust relationship need to exist now, since `environments/dev` will reference `deployment_role_arn` as a future input) but has **no permissions policy attached at all** — not `AdministratorAccess`, not a scoped-down placeholder, nothing. Three additional corrections landed in the same pass: (a) `README.md`'s command order fixed so `terraform init` runs before `terraform validate` (it had been listed backwards); (b) a `lifecycle.precondition` added to `aws_iam_role.deployment` requiring the account segment of `human_bootstrap_principal_arn` to equal `aws_account_id`, failing plan/apply on a mismatch rather than silently trusting a principal from the wrong account; (c) documentation-accuracy fixes — `allowed_account_ids` no longer described as aborting "before any API call" (corrected to: the AWS provider checks the account via STS during provider configuration and prevents subsequent resource-management operations if it doesn't match), the "five hardening resources" wording replaced with an explicit list, and `terraform import` guidance updated to remove the now-nonexistent IAM policy/attachment import lines.
- **Evidence obtained:** Static-review evidence (tier 3).
- **Mistake or issue discovered:** The first correction pass's fix (narrower permissions) was a real improvement over the original placeholder, but was still the wrong end-state — this is recorded here specifically because it's a useful, honest example of iterative correction: the first fix wasn't wrong to attempt, it just didn't go far enough, and a second look caught that.
- **Correction:** See "Result" above.
- **Remaining risk:** A future, separately reviewed change will need to attach a real permissions policy to this role once `environments/dev` exists — that future policy is explicitly **not** `AdministratorAccess` and not a wildcard grant, per the same reasoning that led here.
- **Next gate:** Controlled local `terraform fmt`/`init`/`validate` (Sections 15-20).

## 15. Runtime Terraform Tooling Blocker in Cowork

### Step
- **Goal:** Run the controlled five-command sequence (`terraform version`, `fmt -recursive`, `fmt -check -recursive`, `init -backend=false`, `validate`) from `infrastructure/terraform/bootstrap/`.
- **Action:** Performed pre-command safety checks first (confirmed `backend.tf`'s `s3` block is fully commented out; confirmed `-backend=false` cannot migrate state; confirmed `terraform validate` doesn't require real `terraform.tfvars` values; confirmed none of the five commands creates an AWS resource). Then ran `terraform version` from the Cowork sandbox.
- **Decision:** Per the explicit stop-on-failure rule governing this task: if any command fails, stop immediately, do not modify code to suppress the error, do not continue to later commands.
- **Result:** `terraform version` **failed immediately: `bash: line 1: terraform: command not found` (exit code 127).** Extensive troubleshooting confirmed this was a genuine environment gap, not a code defect: no `terraform` binary installed, no root/sudo access (`apt-get update` denied; `sudo` blocked by the "no new privileges" flag), and every known Terraform/GitHub-release/conda/Docker-Hub distribution source unreachable under the sandbox's network allowlist (`releases.hashicorp.com` → 403 blocked-by-allowlist; `apt.releases.hashicorp.com`, `registry.terraform.io`, `developer.hashicorp.com`, `api.github.com`, `raw.githubusercontent.com`, `codeload.github.com`, `objects.githubusercontent.com`, `anaconda.org`, `conda.anaconda.org`, `repo.anaconda.com`, `registry.hub.docker.com` all blocked/unreachable). No existing `terraform` binary was found anywhere on the filesystem. Commands 2-5 were **deliberately not run.**
- **Evidence obtained:** None beyond the failure itself — this is explicitly a non-event for evidence purposes, not tier 4 "almost."
- **Mistake or issue discovered:** No code defect — this was a tooling/environment availability gap in the Cowork sandbox specifically.
- **Correction:** None applied to the Terraform code (correctly — there was nothing to fix in the code). The correct response was to stop, document the exact blocker, and hand off to a different environment — which is what happened (Section 16).
- **Remaining risk:** None to the code; the risk was entirely "don't let time pressure turn into a workaround that fabricates evidence" — avoided by stopping cleanly.
- **Next gate:** Run the same five-command sequence on a machine that actually has Terraform installed.

## 21. TFLint Installation, Warning, Correction, and Clean Rerun

### Step
- **Goal:** Run static linting against the validated configuration.
- **Action:** TFLint 0.64.0 installed; `tflint --init` run (all plugins already installed); a lint run performed against `bootstrap/`.
- **Decision:** Treat any finding as something to fix in the code, not suppress.

### Step

## 30. Lessons Learned So Far

- **A first correction is not always the last one needed.** Section 13's narrower-permissions fix was a real improvement, but Section 14's harder question ("should this role have this access category at all?") found a better answer. Reviewing a fix, not just the original defect, caught this.
- **An unused variable is often a symptom, not the disease.** The TFLint warning in Section 21 was a direct, mechanical consequence of the Section 14 decision — the tool caught a cleanup step that a purely manual review had missed.
- **A scanner finding is a fact to triage, not a verdict to obey.** Section 23's HIGH-severity Trivy finding was reviewed against this project's actual, already-documented risk tolerance (cost-conscious, single-developer, no-secrets-by-design bucket) rather than fixed reflexively to clear a severity label.
- **Stopping is sometimes the correct engineering action.** Section 15's tooling blocker was resolved correctly by stopping and documenting, not by installing an unverified binary or fabricating a result to satisfy a checklist.
- **Documentation that overclaims is a liability, not a convenience.** Every corrected instance of imprecise wording in this project (Section 14's "before any API call" fix, the "five hardening resources" → explicit list fix, Section 22's refusal to call the scan "clean") exists because a later, more careful read caught language that was technically wrong even though the underlying intent was right.

## 27ad. Self-Assume-Role Recurrence and the Corrected `login.ps1` MFA Workflow (2026-07-26)

The day after the successful apply above, a fresh `terraform apply` from `environments/dev` failed before reaching any resource: `AccessDenied: ... is not authorized to perform sts:AssumeRole on enterprise-data-platform-shared-deployment-role`, with `aws sts get-caller-identity` showing the ambient shell credentials were **already** an assumed-role session for the deployment role itself (session name `terraform-dev`), not the base IAM-user identity `providers.tf`'s own `assume_role` block expects to start from.

**Diagnosis, confirmed against `bootstrap/main.tf`'s trust policy (`deployment_role_trust`) rather than assumed:** the trust policy's single statement trusts only `var.human_bootstrap_principal_arn` (the IAM user), conditioned on `aws:MultiFactorAuthPresent = true` — it does not trust the role's own ARN or any `assumed-role/enterprise-data-platform-shared-deployment-role/*` session as a principal. When the ambient identity is already that assumed-role session, and `providers.tf`'s `assume_role` block then calls `sts:AssumeRole` again against the same role, AWS evaluates the trust policy against the actual caller — the assumed-role session — which is not a principal the trust policy lists at all, so the call is denied. This is a **self-assume/double-assume** failure, not a permissions gap in the role's attached policies, and not something the intended two-hop design (base IAM-user identity → Terraform's own single `AssumeRole`, performed identically by both `providers.tf`'s `session_name = "terraform-dev-provider"` block and `backend.hcl`'s own `session_name = "terraform-dev-backend"` block) was ever expected to produce. **Nothing in the intended authentication flow changed** — the ambient session name observed (`terraform-dev`) matches neither of this project's own two Terraform-driven session names, indicating the ambient credentials were left over from an out-of-band manual assumption (plausibly from earlier diagnostic CLI work in Section 27aa), not from a design change. `providers.tf`'s `assume_role` block was deliberately **not** removed in response — doing so would have broken the documented base-identity-to-role pattern for the normal case (ambient base-user credentials), even though it would have coincidentally worked for this one abnormal case.

**Resolution: a corrected, repeatable `login.ps1` script**, run from the project root before any Terraform command, which the repository already contains at `login.ps1` and which was reviewed and confirmed to already implement every required behavior:

- Clears any old temporary AWS session credential environment variables first (`AWS_SESSION_TOKEN`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`), specifically to prevent this exact stale-assumed-role-session class of failure from recurring.
- Prompts for a fresh MFA code and requests a new session via `aws sts get-session-token` against the human bootstrap principal's own MFA device — **not** `aws sts assume-role` — so the resulting ambient identity is the base IAM user with a temporary MFA-backed session, never an already-assumed role.
- Checks `$LASTEXITCODE` after the STS call and **stops on failure** (`Write-Host "Login failed."` in red, `return`) — the script does not proceed to export credentials or print a success message if `get-session-token` failed.
- Sets `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` from the fresh session response, plus `AWS_REGION`/`AWS_DEFAULT_REGION`.
- Only prints "Login successful." and runs `aws sts get-caller-identity` (as a real, observable confirmation of the resulting identity) after the STS call has already succeeded — never before, and never if it failed.

No change was made to `login.ps1` itself as part of this task — it already matched every behavior the user described as required; this section documents its existing, confirmed-correct behavior rather than introducing new behavior. **Minor observation, flagged rather than silently left unaddressed:** `login.ps1` hardcodes the MFA device's serial-number ARN (including the AWS account ID) directly in a script tracked in this repository, rather than sourcing it from a gitignored variable file the way `terraform.tfvars`/`backend.hcl` do elsewhere in this project. This is not a credential and not Terraform state, so it falls outside `CLAUDE.md`'s explicit "never commit secrets" rule, but it is a real deviation from this project's general pattern of keeping account-specific values out of tracked files — recorded here as a flagged observation, not fixed as part of this documentation task.
